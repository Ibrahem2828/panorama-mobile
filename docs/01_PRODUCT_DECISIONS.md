# قرارات المنتج الأساسية

هذه القرارات ملزمة للمراحل القادمة ما لم يطلب صاحب المشروع تغييرها صراحة.

| القرار                           | السبب                                                             | أثره على تصميم التطبيق                                             | أثره على التطوير                                                 |
| -------------------------------- | ----------------------------------------------------------------- | ------------------------------------------------------------------ | ---------------------------------------------------------------- |
| Arabic-first                     | الجمهور الأساسي عربي، والتجربة يجب أن تبدو أصلية لا مترجمة لاحقا. | النصوص، ترتيب العناصر، المسافات، ونبرة الرسائل تصمم بالعربية أولا. | عدم افتراض الإنجليزية في أسماء الواجهات المرئية أو رسائل الخطأ.  |
| RTL-first                        | العربية تحتاج اتجاها بصريا صحيحا من البداية.                      | القوائم، التبويبات، الأسهم، المحاذاة، وحقول الإدخال تتبع RTL.      | اختبار كل شاشة في RTL وعدم تأجيل الدعم لمرحلة لاحقة.             |
| Mobile-first                     | المنتج الأساسي تطبيق موبايل لا بوابة ويب.                         | الواجهات قصيرة، قابلة للمس، وتراعي الشاشات الصغيرة.                | اختيار مكتبات وأنماط مناسبة لـ React Native وتجربة Android أولا. |
| In-app chat first                | المحادثات جزء من قيمة الغروبات داخل التطبيق.                      | تظهر المحادثة كجزء طبيعي من تفاصيل الغروب.                         | تجهيز خدمة WebSocket ونموذج رسائل واضح من البداية.               |
| روابط واتساب مساندة              | بعض الغروبات قد تحتاج قناة خارجية، لكنها ليست مصدر الحقيقة.       | رابط واتساب يظهر داخل وصف الغروب عند توفره فقط.                    | الرابط حقل اختياري من API، ولا تبنى عليه صلاحيات أو منطق رئيسي.  |
| لا يوجد زر تنزيل مباشر للملفات   | تقليل مشاركة الملفات خارج التطبيق وتحسين التحكم بالتجربة.         | صفحة الملف تعرض فتح داخل التطبيق أو طلب طباعة.                     | PDF Viewer مطلوب، ولا تضاف أزرار download في MVP.                |
| خدمات الطباعة ديناميكية          | الأسعار والخدمات تتغير تشغيليا.                                   | شاشات الطباعة تعرض الخيارات القادمة من API.                        | لا تستخدم قيم hardcoded إلا كـ fallback مؤقت موثق.               |
| الإدارة تتحكم بالطباعة والأسعار  | الطباعة عملية تشغيلية تحتاج تعديلا مستمرا.                        | المستخدم يرى خيارات متاحة فقط حسب الإعدادات الحالية.               | API الطباعة يجب أن يدعم الخدمات، الأسعار، وأماكن الاستلام.       |
| التوثيق يفتح الميزات الحساسة     | بعض الميزات يجب أن تكون للطلاب المقبولين فقط.                     | تظهر حالات Pending/Rejected/Verified بوضوح.                        | كل شاشة حساسة تتحقق من حالة المستخدم القادمة من الباك إند.       |
| الباك إند مصدر الحقيقة للصلاحيات | إخفاء زر في الواجهة ليس حماية كافية.                              | الواجهة تعرض فقط ما يسمح به الباك إند.                             | كل طلب API يجب أن يعالج 401/403 وحالات الرفض.                    |
| تجنب تضخم MVP                    | النسخة الأولى يجب أن تصل بسرعة إلى تجربة مستقرة.                  | لا تضاف ميزات متقدمة تربك الطالب.                                  | تقسم الميزات المتقدمة إلى مراحل لاحقة.                           |
| المحادثة في v1 نصية فقط          | تقليل التعقيد التشغيلي والتقني.                                   | واجهة المحادثة تركز على قراءة وإرسال النصوص.                       | لا تنفذ voice messages أو reactions أو read receipts في MVP.     |
| الإشعارات الداخلية أولا          | Push يحتاج إعدادات إنتاجية أوسع، ومركز داخلي يكفي كبداية.         | تبويب أو شاشة إشعارات واضحة داخل الحساب.                           | يمكن تجهيز abstraction للإشعارات دون إلزام Push في أول إصدار.    |

## ملاحظات تنفيذية

- أي قرار متعلق بالصلاحيات أو الأسعار أو الخدمات يجب أن يكون قابلا للتعديل من الباك إند.
- أي شاشة تعرض بيانات حساسة يجب أن تتعامل مع حالات عدم التوثيق وعدم الصلاحية.
- واجهة المستخدم يجب أن تحترم الهوية البصرية المعتمدة ولا تستخدم ألوانا عشوائية.
