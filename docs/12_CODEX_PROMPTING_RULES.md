# قواعد استخدام Codex في المراحل القادمة

هذه القواعد تهدف إلى منع الخلط بين المراحل وحماية قرارات Phase 0.

## قواعد عامة

- لا تنفذ أكثر من مرحلة في Prompt واحد.
- لا تغير قرارات Phase 0 إلا إذا طلب المستخدم ذلك صراحة.
- لا تنشئ ميزات خارج نطاق المرحلة المطلوبة.
- لا تضف كودا تطبيقيا عند طلب وثائق فقط.
- لا تثبت dependencies دون طلب واضح أو حاجة موثقة.

## قواعد المنتج والتصميم

- لا تستخدم ألوانا خارج الهوية البصرية.
- احترم RTL في كل شاشة.
- لا تضف زر تنزيل للملفات.
- لا تجعل خدمات الطباعة hardcoded إذا كان يمكن جعلها ديناميكية.
- لا تعتمد على رابط واتساب كبديل للمحادثة الداخلية.
- لا توسع MVP بميزات مؤجلة مثل voice messages أو payments دون طلب.

## قواعد المعمارية

- استخدم TypeScript types لكل شيء.
- حافظ على Feature-based architecture.
- لا تكتب API calls عشوائية داخل الشاشات.
- كل API يجب أن يمر من API Client.
- استخدم TanStack Query لحالة الخادم.
- استخدم Zustand فقط للحالة المحلية أو Auth/UI الخفيفة.
- لا تخزن tokens في AsyncStorage.
- استخدم SecureStore لتخزين tokens.
- لا تضع أسرار داخل الكود.

## قواعد الشاشات

- كل شاشة يجب أن تدعم Loading وError وEmpty.
- كل شاشة حساسة يجب أن تتعامل مع Permission Denied.
- لا تفترض أن المستخدم موثق إلا من حالة الباك إند.
- لا تعتمد على إخفاء الأزرار فقط للصلاحيات.
- رسائل الخطأ يجب أن تكون عربية ومفهومة.

## قواعد النماذج

- كل نموذج يجب أن يستخدم validation.
- رسائل validation يجب أن تكون عربية.
- لا ترسل بيانات ناقصة إلى API إذا يمكن اكتشافها في الواجهة.
- لا تكرر validation logic بين الشاشات دون سبب.

## قواعد الملفات والطباعة

- فتح الملفات يكون داخل التطبيق في MVP.
- الملفات قد تحتاج Authorization.
- خيارات الطباعة والأسعار وأماكن الاستلام تأتي من API.
- عند تغير السعر قبل إرسال الطلب يجب عرض تنبيه أو تحديث الملخص.

## قواعد المراجعة

- قبل إنهاء أي مرحلة، راجع الملفات المطلوبة من الوثائق.
- تأكد من عدم إنشاء `package.json` في مراحل الوثائق.
- تأكد من عدم إضافة dependencies دون موافقة.
- اذكر بوضوح ما تم وما لم يتم تنفيذه.
