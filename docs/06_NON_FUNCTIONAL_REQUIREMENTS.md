# المتطلبات غير الوظيفية

## الأداء

- يجب أن تفتح الشاشات الأساسية بسرعة مع استخدام Skeleton عند الحاجة.
- يجب تقليل إعادة التصيير غير الضرورية في القوائم والمحادثات.
- يجب تحميل القوائم بصفحات Pagination عند وجود عدد كبير من العناصر.
- يجب ضغط الصور والمرفقات من جهة الباك إند أو عند الرفع حسب الحاجة.

## الأمان

- تخزين tokens يجب أن يكون عبر SecureStore وليس AsyncStorage.
- لا توضع أسرار أو مفاتيح خاصة داخل الكود.
- كل طلب حساس يجب أن يعتمد على Bearer Token.
- الصلاحيات يجب أن تطبق في الباك إند، مع تعامل الواجهة مع 401 و403.

## الخصوصية

- لا تعرض بيانات طالب لطالب آخر.
- لا ترسل معلومات حساسة في logs.
- يجب توضيح سياسة الخصوصية قبل الإنتاج.
- الملفات والمستندات الجامعية تعامل كبيانات حساسة.

## الاعتمادية

- يجب أن تتعامل الشاشات مع ضعف الإنترنت وانقطاعه.
- WebSocket يجب أن يدعم reconnect بتدرج منطقي.
- فشل خدمة معينة لا يجب أن يكسر كامل التطبيق.

## قابلية التوسع

- المعمارية يجب أن تكون Feature-based.
- خدمات الطباعة والأسعار وأماكن الاستلام يجب أن تكون ديناميكية.
- المحادثات يجب أن تصمم بحيث يمكن تطويرها لاحقا دون إعادة كتابة كاملة.

## سهولة الاستخدام

- النصوص عربية واضحة ومباشرة.
- الإجراءات الأساسية لا تحتاج خطوات زائدة.
- يجب استخدام أزرار وحالات مرئية مفهومة.
- رسائل الخطأ يجب أن تخبر المستخدم بما يمكن فعله.

## دعم RTL

- RTL ليس إضافة لاحقة؛ هو الافتراض الأساسي.
- يجب اختبار المحاذاة، الأسهم، التبويبات، والحقول.
- لا تستخدم أيقونات اتجاهية دون عكسها عند الحاجة.

## قابلية الصيانة

- كل Feature تملك ملفاتها ومنطقها محليا.
- API calls تمر عبر API Client موحد.
- لا تكرر منطق الصلاحيات أو التنسيق بين الشاشات.
- أسماء الأنواع والدوال يجب أن تكون واضحة.

## جودة الكود

- استخدام TypeScript إلزامي في مرحلة التنفيذ.
- يجب تعريف types للـ API responses والـ models.
- استخدام validation للنماذج عبر Zod أو ما يعادله.
- منع الملفات الكبيرة التي تجمع منطق واجهات وخدمات وحالة في مكان واحد.

## قابلية الاختبار

- يجب تصميم المنطق بحيث يمكن اختبار services وstores وvalidation.
- الحالات الأساسية لكل شاشة يجب أن تكون قابلة للمحاكاة.
- flows الحساسة مثل التوثيق والطباعة والدخول تحتاج اختبارات لاحقا.

## إدارة الأخطاء

- كل شاشة يجب أن تعرض Error State واضحا.
- أخطاء API يجب أن تحول إلى رسائل عربية مناسبة.
- أخطاء 401 تؤدي إلى refresh token عند الإمكان.
- فشل refresh يؤدي إلى logout آمن.

## التعامل مع ضعف الإنترنت

- عرض حالة اتصال أو رسالة عند الفشل.
- دعم retry في القوائم والملفات.
- المحادثة يجب أن توضح حالة الإرسال أو الفشل.

## جاهزية الإنتاج

- لا توجد dev URLs داخل production build.
- يجب ضبط Versioning وChangelog.
- يجب اختبار APK preview قبل إنتاج AAB.
- يجب تجهيز Privacy Policy وTerms وبيانات Google Play.

## مراقبة الأخطاء لاحقا

- يفضل تجهيز مكان لإضافة خدمة مراقبة أخطاء لاحقا.
- يجب عدم إرسال بيانات حساسة ضمن تقارير الأخطاء.
- الأخطاء المهمة في المحادثة والطباعة والتوثيق يجب أن تكون قابلة للتتبع.
